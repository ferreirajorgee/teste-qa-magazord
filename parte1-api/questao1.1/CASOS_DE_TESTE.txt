--------------------------------------------------------------------------------
1. ESCOPO
--------------------------------------------------------------------------------

Itens do enunciado (usados na rastreabilidade):

  I1  Validar os headers X-RateLimit-Limit, X-RateLimit-Remaining e
      X-RateLimit-Reset da GitHub API (GET /users/github).
  I2  Detectar quando o rate limit foi atingido (403).
  I3  Login no ReqRes (POST /api/login), obtendo o token e reutilizando-o em
      requisição autenticada (GET /api/users/2 com Authorization: Bearer).
  I4  Simular a expiração do token (TTL fixo de 2 minutos) e validar o
      tratamento do erro.

Dentro do escopo:
  - Contrato e coerência dos headers de rate limit da GitHub API.
  - Classificação de respostas 403/429 (rate limit x outras causas) e cálculo
    do tempo de espera.
  - Login, reutilização do token em cache, erros de login.
  - Expiração do token pelo TTL, renovação automática e erro claro.

Fora do escopo:
  - Carga e concorrência contra as APIs públicas (seria abuso de serviço de
    terceiros e não é controlável).
  - Validação real de expiração no servidor: o token do ReqRes é fixo e não
    expira (ver Gaps).
  - Endpoints do GitHub com outros recursos de cota (search, graphql).


--------------------------------------------------------------------------------
2. REGRAS IDENTIFICADAS
--------------------------------------------------------------------------------

Do enunciado:
  RN01  GitHub sem autenticação: 60 requisições por hora.
  RN02  GitHub com autenticação: 5000 requisições por hora.
  RN03  Ao exceder o limite, a GitHub API responde 403.
  RN04  POST /api/login com credenciais válidas retorna um token.
  RN05  O token é usado no header Authorization: Bearer {token}.
  RN06  O token tem curta duração (simulada: 2 minutos) e deve ser reutilizado
        enquanto válido, sem login a cada teste.

Da documentação pública da GitHub API (comportamento verificável):
  RI01  Respostas trazem X-RateLimit-Limit, -Remaining, -Used, -Reset (epoch
        em segundos) e -Resource.
  RI02  Limite primário excedido: 403 ou 429, Remaining = 0, mensagem
        "API rate limit exceeded".
  RI03  Limite secundário: 403 ou 429 com mensagem "secondary rate limit" e,
        quando presente, Retry-After.

Observadas no ReqRes em 06/10/2026 (dependência externa, não do enunciado):
  RI04  Chamadas enviam x-api-key (chave gratuita reqres-free-v1).
  RI05  Login sem senha: 400 {"error":"Missing password"}.
  RI06  Login com usuário inexistente: 400 {"error":"user not found"}.
  RI07  Authorization: Bearer em /api/users/2 é recusado com 401, inclusive
        com o token do /login. Sem o header, o recurso responde 200.
  RI08  O ReqRes também limita: 20 req/min e cota diária na chave gratuita.

Regras de projeto (decisão de implementação):
  RP01  Token expirado quando (agora - obtidoEm) >= TTL (borda fechada).
  RP02  Token expirado é renovado antes de enviar a requisição autenticada.
  RP03  Quem exige token válido sem renovar recebe erro claro:
        "Token expirado: obtido há X ms, TTL de Y ms."
  RP04  403 que não é de rate limit NÃO pode ser tratado como rate limit.


--------------------------------------------------------------------------------
3. ESTRATÉGIA (ORIENTADA A RISCO)
--------------------------------------------------------------------------------

Riscos considerados:

  R01  CRÍTICO  Tratar qualquer 403 como rate limit (ou nenhum): esconde
                falha de permissão ou deixa o bloqueio sem diagnóstico.
  R02  ALTO     Headers de rate limit ausentes ou incoerentes: o cliente não
                consegue se autorregular e é bloqueado.
  R03  ALTO     Token reutilizado depois de expirar: chamadas falham com 401
                em produção.
  R04  ALTO     Login a cada teste: lentidão e consumo da cota do ReqRes
                (limite diário da chave gratuita).
  R05  MÉDIO    Cálculo errado do tempo de espera (Retry-After x Reset).
  R06  MÉDIO    Erros de login sem mensagem clara.
  R07  ALTO     Testes destrutivos ou instáveis: esgotar 60 req/h derruba os
                demais testes do mesmo IP por até 1 hora.

Decisões:

  1. Pirâmide: a regra de decisão (classificar resposta, calcular espera,
     expiração) é testada em funções puras com respostas simuladas (camada
     "unitário", custo zero de cota, determinística). As chamadas reais validam
     só o contrato.
  2. cy.intercept não intercepta cy.request; por isso a simulação é feita
     passando respostas simuladas diretamente às funções do helper.
  3. Esgotamento real do GitHub (CT-RL-11) é opcional, anônimo e isolado.
  4. Testes reais toleram a cota já esgotada no ambiente: os headers chegam
     também no 403, e a classificação precisa ser coerente com o status.
  5. Expiração simulada com relógio injetado no gerenciador de token
     (sem cy.wait, sem esperar 2 minutos). cy.clock não se aplica: controla
     só o relógio da aplicação no navegador.
  6. Comparação do Reset com o header Date do servidor, não com o relógio
     local, para não depender do ajuste do relógio da máquina.
  7. Chamadas reais ao ReqRes por execução completa: 8.

Prioridades:
  P0  Falha impede o fluxo principal ou causa diagnóstico errado.
  P1  Comportamento importante ou risco significativo.
  P2  Borda e complementares.

Tags: @smoke (P0 rápidos), @api (chamada real), @unitario (sem rede),
      @rate-limit, @token, @destrutivo (opcional).

Pré-condições gerais:

Feature: Rate limit da GitHub API

  CT-RL-01 | P0 | Positivo | API real | I1 | R02, R07
  Pré-condição: PC01.
  Scenario: Retornar os headers de rate limit com valores coerentes
    Given a GitHub API está acessível
    When o cliente consulta o usuário "github"
    Then a resposta deve ser 200, ou 403/429 se a cota do ambiente já estiver
      esgotada, com a classificação de bloqueio coerente com o status
    And X-RateLimit-Limit deve ser um inteiro positivo
    And X-RateLimit-Remaining deve estar entre 0 e o limite
    And X-RateLimit-Used deve ser igual a Limit - Remaining
    And X-RateLimit-Reset deve estar no futuro e no máximo 1 hora à frente
      da data do servidor
    And X-RateLimit-Resource deve ser "core"

  CT-RL-02 | P1 | Positivo | API real | I1 | R02
  Pré-condição: PC01, PC03.
  Scenario: Aplicar o limite correspondente ao modo de autenticação
    Given o GITHUB_TOKEN está vazio ou preenchido
    When o cliente consulta o usuário "github"
    Then X-RateLimit-Limit deve ser 60 sem token
    And deve ser 5000 com token

  CT-RL-03 | P1 | Positivo | API real | I1 | R02
  Scenario: Decrementar o Remaining a cada requisição consumida
    Given o cliente fez uma consulta e registrou o Remaining
    When faz uma nova consulta na mesma janela
    Then o Remaining deve ter diminuído pelo menos 1, sem ficar negativo
    And o Reset deve ser o mesmo (mesma janela)
  Observação: "pelo menos 1" porque outros processos do mesmo IP podem
    consumir cota em paralelo.

  CT-RL-04 | P0 | Negativo | Unitário | I2 | R01, R05
  Scenario: Identificar 403 com Remaining 0 como rate limit primário
    Given uma resposta 403 com Remaining 0, Used 60, Reset em 10 minutos
      e a mensagem "API rate limit exceeded for 203.0.113.10."
    When a resposta é analisada
    Then deve ser classificada como rate limit primário
    And a cota deve constar como esgotada
    And a espera calculada deve ser 600000 ms

  CT-RL-05 | P1 | Negativo | Unitário | I2 | R05
  Scenario: Priorizar o Retry-After no cálculo da espera
    Given uma resposta 429 com Retry-After 30 e um Reset em 10 minutos
    When a resposta é analisada
    Then deve ser classificada como rate limit
    And a espera deve ser 30000 ms

  CT-RL-06 | P1 | Negativo | Unitário | I2 | R01
  Scenario: Identificar o rate limit secundário com cota primária disponível
    Given uma resposta 403 com Remaining 42, Retry-After 60
      e a mensagem "You have exceeded a secondary rate limit."
    When a resposta é analisada
    Then deve ser classificada como rate limit secundário
    And a espera deve ser 60000 ms

  CT-RL-07 | P0 | Negativo | Unitário | I2 | R01
  Scenario: Não tratar como rate limit um 403 por falta de permissão
    Given uma resposta 403 com Remaining 4990
      e a mensagem "Resource not accessible by personal access token"
    When a resposta é analisada
    Then não deve ser classificada como rate limit
    And o motivo deve ser "acesso negado", sem tempo de espera

  CT-RL-08 | P2 | Borda | Unitário | I2 | R05
  Scenario: Sinalizar cota esgotada na última requisição atendida
    Given uma resposta 200 com Remaining 0
    When a resposta é analisada
    Then não deve ser classificada como bloqueada
    And deve sinalizar que a cota está esgotada para a próxima chamada

  CT-RL-09 | P2 | Borda | Unitário | I2 | R05
  Scenario: Retornar espera zero quando o reset já passou
    Given uma resposta 403 de rate limit com Reset 5 segundos no passado
    When a resposta é analisada
    Then a espera deve ser 0 ms

  CT-RL-10 | P1 | Positivo | API real | I1, I2 | R01, R07
  Scenario: Classificar a resposta real de forma coerente com a cota
    Given a GitHub API está acessível
    When o cliente consulta o usuário "github"
    Then, se a resposta for 200, não deve estar classificada como bloqueada
      e o corpo deve trazer o login "github"
    And, se for 403/429, deve estar classificada como rate limit, com
      mensagem citando rate limit e espera calculável

  CT-RL-11 | P2 | Negativo | API real (opcional, destrutivo) | I2 | R01, R07
  Pré-condição: npm run test:destrutivo (spec isolado) e cota anônima > 0,
    verificada em GET /rate_limit (sem consumir cota). Consome a cota
    anônima do IP por até 1 hora.
  Scenario: Receber 403 ao exceder o limite anônimo real
    Given o cliente faz chamadas anônimas consecutivas
    When a cota de 60 requisições é excedida
    Then a resposta deve ser 403, classificada como rate limit primário
    And a mensagem deve conter "API rate limit exceeded"
    And o Remaining deve ser 0
    And a espera deve estar dentro da janela de 1 hora (relógio do servidor)
    And a requisição anterior deve ter sido atendida (200) com Remaining 0
    And o bloqueio deve ocorrer em no máximo (cota inicial + 1) requisições

9. GAPS
--------------------------------------------------------------------------------

Gaps:
  G01  O ReqRes não expira o token no servidor: a expiração é só do lado do
       cliente (TTL). A detecção por 401 é coberta apenas com resposta
       simulada (CT-TK-11) e com o 401 atual do Bearer (CT-TK-03).
  G02  O ReqRes atual recusa Authorization: Bearer em /api/users/2 (RI07);
       não há hoje um caminho real de "requisição autenticada com sucesso".
  G03  O 403 real de rate limit só é validado no CT-RL-11, opcional.
  G04  O ReqRes aceita qualquer senha para eve.holt@reqres.in; "senha
       incorreta" não é testável nessa API.
  G05  A chave pública reqres-free-v1 tem cota de 40 req/dia por IP. Com a
       cota esgotada (429), os CT-TK de API real falham como INCONCLUSIVO,
       sem validar a regra; o resultado só vale após o reset (00:00 UTC) ou
       com uma chave própria.

10. RESUMO DE COBERTURA
--------------------------------------------------------------------------------

  Itens do enunciado cobertos: I1, I2, I3, I4 (4 de 4).
  Regras cobertas: RN01-RN06, RI01-RI07, RP01-RP04. RI08 (rate limit do
    ReqRes) é tratado na mensagem de erro do login, sem caso dedicado.
  Positivos: 10 | Negativos: 9 | Borda: 3.
  Integrações: GitHub API e ReqRes (chamadas reais), com fallback para
    cota esgotada.
  Autenticação: token GitHub opcional (limite 5000) e token ReqRes
    (login, reutilização, expiração, renovação, 401).
